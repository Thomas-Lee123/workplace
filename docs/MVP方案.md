# 一键旅行 MVP 方案

## 一、产品定位

**旅行行程"购物车"** — 用户在携程、马蜂窝、飞猪等平台浏览时，把心仪的酒店、门票、景点一键收藏到统一的行程里，按天组织，最终逐个跳回源平台完成购买。

### MVP 核心价值

> 分散收藏 → 统一规划 → 逐个下单

不是替代携程/12306，而是在**它们之上加一层行程编排层**。

---

## 二、MVP 做什么、不做什么

| 做 | 不做 |
|---|------|
| 接收用户从其他App分享的链接 | 自动化登录、下单、支付 |
| 解析链接提取结构化信息 | 服务端主动搜索/爬取平台 |
| 按天组织行程 | 自动跨平台比价 |
| 手动标记已购/未购 | 价格追踪和降价提醒 |
| 一键跳回源平台完成购买 | 多人协作 |
| 行程分享（截图/链接） | 推荐/攻略内容 |

## 三、核心流程

```
用户在携程/马蜂窝 App 看到商品
        ↓
    点击"分享/转发"
        ↓
    在分享面板选择"一键旅行"
        ↓
  App 接收链接，服务端解析
  提取：标题、类型、价格、日期、图片、来源平台
        ↓
  用户确认信息，选择归入哪一天
        ↓
    加入行程"购物车"
        ↓
  行程全景视图：
  Day 1 — 🏨 XX酒店 ¥1280  ⬜待购
  Day 1 — 🎫 XX景点 ¥150  ✅已购
  Day 2 — 🚄 G123 北京→上海  ⬜待购
        ↓
  点击某个项目 → 跳回源平台App完成支付
  回来后手动标记"已购"
```

## 五、链接解析策略

### 为什么 OG 标签层比你想象的稳定

OG（Open Graph）标签是给微信、微博、Facebook 等社交平台看的——分享链接时展示的标题、描述、图片就靠它。如果携程改了 OG 标签，微信里分享出来的酒店卡片就会显示异常，影响的是**所有用户分享到微信的体验**。所以大平台对 OG 标签的改动非常谨慎，这是他们自己的核心利益。

**OG 标签覆盖率高且稳定，是第一道也是最可靠的一道防线。**

---

### 四层解析 + 兜底

```
稳定性高 ┌──────────────────────────┐
         │ 1. OG/Meta 标签           │  平台不敢随便动
         │    （改动会影响微信分享）   │
         ├──────────────────────────┤
         │ 2. JSON-LD 结构化数据      │  标准格式，搜索引擎用
         ├──────────────────────────┤
         │ 3. AI 兜底解析             │  把 HTML 喂给 LLM 提取
         │    （零维护规则，有调用成本）│
         ├──────────────────────────┤
         │ 4. HTML 规则提取           │  最后手段，按需编写
         │    （最脆弱，尽量少依赖）   │
稳定性低 └──────────────────────────┘
```

---

### AI 兜底解析

核心思路：前两层（OG + JSON-LD）覆盖 80%+ 场景且免费、极快。失败或信息不全时，把 HTML 文本丢给 LLM：

```
Prompt:
从以下 HTML 片段中提取旅游商品信息：
- 商品标题
- 类型（hotel/attraction/traffic/other）
- 价格
- 图片URL
- 日期（如有）

只返回 JSON 格式，找不到的字段填 null。

HTML: <html>......</html>
```

**优点：**
- 不依赖任何选择器，HTML 怎么改都无所谓
- 一套逻辑覆盖所有平台，包括未适配的新平台
- 新增平台零开发成本

**缺点：**
- API 调用有延迟（1-3 秒）和费用
- 偶尔提取不准确，返回低置信度标记
- 依赖 LLM 服务可用性

**平衡方案：** OG + JSON-LD 走快速路径（<100ms），提取不完整时再走 AI（1-3s），绝大多数正常请求秒级返回。

---

### 解析器架构

每个平台一个独立解析器，互不影响，统一接口：

```typescript
interface Parser {
  parse(html: string, url: string): Promise<ParseResult>
}

interface ParseResult {
  title: string | null
  type: 'hotel' | 'attraction' | 'traffic' | null
  price: number | null
  imageUrl: string | null
  date: string | null
  source: Platform
  confidence: 'high' | 'medium' | 'low'
}
```

```
parsers/
  ├── ctrip.ts         携程
  ├── mafengwo.ts      马蜂窝
  ├── fliggy.ts        飞猪
  ├── meituan.ts       美团
  ├── qunar.ts         去哪儿
  └── fallback.ts      通用（OG + JSON-LD + AI）
```

**解析流程：**

```
URL 进入
  ↓
识别平台（根据域名）
  ↓
┌─ 有专属解析器？
│    ↓
│  先走 OG/JSON-LD 快速路径（<100ms）
│    ↓ 信息不全或置信度低
│  走 AI 兜底（1-3s）
│
└─ 无专属解析器？
     ↓
  直接用通用 fallback（OG + JSON-LD + AI）
```


### 维护成本估算

| | 初始开发 | 日常维护 |
|------|---------|---------|
| 携程解析器 | 0.5 天 | 每年 2-3 次适配，每次 1-2h |
| 马蜂窝解析器 | 0.5 天 | 同上 |
| 飞猪解析器 | 0.5 天 | 同上 |
| AI 兜底 | 1 天 | 无（只管 API 付费） |
| 监控告警 | 1 天 | 无 |

**结论：初始 3-4 天搭完解析框架，后续维护成本很低。** OG + AI 双层保险意味着 HTML 改版不需要立刻修，AI 自动兜底，你挑个周末集中适配就行。

### 解析结果字段

- title：商品标题（必填）
- type：自动推断 hotel / attraction / traffic（选填，用户可改）
- price：价格数字
- imageUrl：封面图
- date：如果页面有日期信息则提取
- confidence：置信度（高 → 直接展示；中/低 → 展示+提示用户确认）

### 支持的平台（MVP 按优先级）

1. 携程 — 酒店、门票、跟团游
2. 马蜂窝 — 酒店、景点
3. 飞猪 — 酒店、门票
4. 12306 — 车次分享页（如果有分享功能）

## 九、技术栈

| 层 | 选择 | 理由 |
|----|------|------|
| 前端 | **React + Vite** | 生态成熟，开发快 |
| 后端 | **Node.js + Express + TypeScript** | HTML 解析库最成熟，已经装好 |
| 数据库 | **PostgreSQL** + JSONB 存 meta | 已在服务器运行 |
| ORM | **Prisma** | 类型安全，迁移方便 |
| 认证 | **JWT + bcrypt** | 无状态，适合单服务器 |
| 部署 | 阿里云 ECS，Nginx + PM2 | 已配置完成 |

> MVP 先做网页版，图片存源链接（携程 CDN），不需要自建图片存储。

目标：用户复制携程/马蜂窝链接 → 打开网页 → 自动识别 → 确认信息 → 加入行程。

## 十一、V2 展望（MVP 之后）

- **价格追踪**：服务端定时回访已收藏链接，降价推送通知
- **商品状态监控**：售罄/下架/变更提醒，引导用户找替代
- **自动比价**：服务端搜索多个平台匹配同一商品
- **多人协作**：一家人的行程共享编辑
- **日历同步**：行程导出到系统日历
